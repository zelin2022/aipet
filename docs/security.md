# Security and privacy model

This application is designed for private local use around development tools with sensitive source code, conversations, and authenticated sessions. The companion needs visual assets, local preferences, a foreground provider hint, and small activity labels. It does not need conversation contents or access to AI accounts.

## Data minimization

| Input or storage | Permitted data | Excluded data |
| --- | --- | --- |
| Visual assets | Bundled original sprites and attribution | Remote image URLs or executable upstream content |
| Presence and fullscreen detection | Allowlisted process basenames mapped to providers; foreground fullscreen monitor geometry | Window titles, terminal text, arguments, executable paths, screenshots, process memory |
| Desktop activity inbox | Allowlisted provider/state, hashed session ID, timestamp and schema version | Prompts, transcripts, tool arguments/results, source code, environment variables, credentials |
| Local preferences | Appearance, position, behavior and integration settings | AI account tokens, cookies, project paths, conversation history |
| Sprite usage | Bundled sprite IDs/content hashes, aggregate display counts and visible milliseconds, collection/save timestamps | AI activity history, conversations, project/session identifiers, window titles, attention or occlusion tracking |
| Diagnostics | Minimal local startup/validation failures if needed | Raw event bodies, user text, analytics or crash uploads |

No upstream CrossPet code is an executable dependency. The original asset license and attribution are preserved separately. No CrossPet installer, hook, plugin, preparation tool, or update mechanism should be executed.

## Renderer containment

Every application window must set `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, and `webSecurity: true`. Do not enable the webview tag or insecure content. The renderer has no Node filesystem/process APIs. A restrictive Content Security Policy permits only local scripts and required local media; `connect-src 'none'`, `object-src 'none'`, and `frame-src 'none'` remove unnecessary surfaces. There is no remote application content.

The main process denies permission requests and checks, new windows, unexpected navigation, and downloads. Chromium session requests are blocked for remote schemes. These are defense layers; Node APIs in the main process are not controlled by renderer CSP or a session web-request filter. Main-process code must itself avoid outbound network clients. Electron's [security recommendations](https://www.electronjs.org/docs/latest/tutorial/security), [sandbox model](https://www.electronjs.org/docs/latest/tutorial/sandbox), [session API](https://www.electronjs.org/docs/latest/api/session), and [web-request API](https://www.electronjs.org/docs/latest/api/web-request) describe the relevant boundaries.

The preload must expose one function for each approved action, never generic `send`, `invoke`, `require`, shell execution, arbitrary paths, or raw Electron objects. Main handlers validate the sending web contents and frame plus every argument. An untrusted event cannot select scripts, commands, file paths, or URLs. Numeric values are finite and clamped; enums and booleans are strict; strings and event bodies are bounded.

## Local activity interface

The adapter writes an atomic JSON snapshot per provider/session into `%USERPROFILE%\.aipet\events`. This stable user-profile location avoids LocalAppData virtualization by Windows Store hosts. The app additionally reads only exact legacy Aipet inboxes: `%LOCALAPPDATA%\Aipet\events` and `LocalCache\Local\Aipet\events` under the known `Claude_pzs8sxrjxfjjc`, `OpenAI.Codex_2p2nqsd0c76g0`, and `OpenAI.CodexPrimaryRuntime.v26-1007-641-0_3k8sg7r9htsxt` package families. It does not enumerate provider content stores. Existing sanitized preferences may migrate from those same Aipet directories; no other settings are read.

There is no TCP/HTTP listener and no activity payload sent over a network. Files contain only `version`, `provider`, `state`, a pseudonymized `session`, and `at`. The desktop reader rejects extra fields so accidental transcript forwarding fails closed, reads at most 1,025 bytes before rejecting events over 1,024 bytes, and never logs rejected bodies. It ignores symbolic links and requires the provider/session to match a canonical filename. Polls do not overlap. Each inbox removes valid expired events after 15 minutes and retains the newest 128 valid files. Invalid or unrelated files are left untouched. Paths and commands cannot be selected by an activity event.

The recommended hook commands use fixed `--provider` and `--state` arguments with `--hook`; they never read or parse stdin. For Claude only, the bridge reads the exact documented `CLAUDE_CODE_SESSION_ID` environment variable, hashes it, and uses that pseudonym to separate chats. It does not enumerate the environment. Missing or oversized identifiers and fixed Codex hooks use an anonymous provider slot. No raw identifiers or tool-specific content are stored. The provider may still supply sensitive bytes to the OS pipe, but the adapter does not consume them.

On-demand diagnostics write one bounded, atomically replaced `.aipet/status.json` only after a local status request. The report contains Aipet's process ID, timestamps, polling counters, fixed provider/state enums, window health and the two pets' DOM states. It contains no session identifiers, hook payloads, conversation text or arbitrary error strings. There is no periodic diagnostic log, server or port. A fixed internal DOM query reads only Aipet's own two companion slots with a 750 ms response deadline; it grants no new renderer IPC capabilities. This is same-user troubleshooting metadata, not a separate security boundary.

An independently enabled debug recording adds a temporary, bounded local metadata trace. It is off by default; an immediate capture expires within 15 minutes. An explicit scheduled capture can span at most 30 minutes, starts no more than 24 hours ahead, and checks its start/end clock boundaries on every write. It needs no midpoint renewal. Records contain only allowlisted stages, providers and states, timestamps, and optional hashed workspace labels from the hook process's own working directory. No project file is opened for those labels, and raw directory paths and session IDs are excluded. The trace never consumes hook stdin or copies raw hook payloads. Recording expiry ends new writes; the bounded trace remains available until replaced by a new recording or explicitly removed. This timing/correlation metadata remains accessible to other programs running as the same Windows user. Debug logging is passive and cannot approve tools, launch commands or change AI settings.

Optional `--source` mode has a different privacy boundary. Provider hook protocols may deliver a complete JSON payload to stdin, including fields that contain sensitive content. This mode receives and parses up to 64 KiB transiently, with a 750 ms input deadline, but selects only hook name, tool name, session ID, and notification type. It does not inspect prompt/tool content or open transcript/project paths. Only the minimized event is persisted or forwarded. Hook output is passive empty JSON, including on failure, so the companion cannot approve or reject AI actions. Optional source mode offers tool-specific mapping and pseudonymous sessions with minimal retention; it is not a claim that sensitive bytes never enter adapter memory.

The inbox relies on the Windows user-profile directory's inherited access rules. Node's POSIX file modes are not a substitute for Windows ACL enforcement. Other processes running as the same Windows user may forge events or inspect user-accessible files. Treat activity as an untrusted animation hint, never as authorization or proof of an AI action. Size/count/lifetime bounds reduce malformed input and denial of service but do not make this an isolation boundary against a compromised account. A future named pipe with explicit owner ACLs may strengthen local access control if required.

No third-party hooks are imported, and no real Claude/Codex configuration is changed during installation or app startup. **Connect Codex** is an explicit user action exposed through a dedicated, argument-free IPC method available only to the studio. The main process selects the current user’s `hooks.json` under `CODEX_HOME` or `%USERPROFILE%\.codex`; the renderer cannot choose a file or supply commands. Configuration reads are bounded, local regular files are required, and malformed or unsafe configuration is refused. An existing file’s exact bytes are backed up before a guarded write. Unchanged repeated connections do not write a file or create a backup.

Connection preserves unrelated settings and hook handlers, replaces only confidently recognized fixed Aipet definitions, and leaves ambiguous or customized policy commands untouched. It does not execute existing configuration, approve tools, edit `config.toml`, change project settings or modify host trust records. A registered-hook result is separate from the observed activity indicator. The user must inspect and trust new or changed definitions in Codex; Aipet never edits or bypasses that decision. Claude setup remains manual. The separate source setup utility is also explicit, preserves unrelated settings and backs up existing bytes. See [connection details and the installation record](integrations.md).

## Local sprite counters

The user-requested Sprite usage feature stores only a bounded aggregate at `%USERPROFILE%\.aipet\sprite-usage.json`: at most 512 known sprite IDs with asset hashes, display counts and visible durations, plus collection/save timestamps, within 256 KiB. Only the pet renderer can report current bundled image IDs through its narrow validated IPC; the main process supplies the clock and checks provider/character identity and pet-window visibility. Studio images and activity previews do not contribute. Nothing is uploaded, no timeline of image changes is retained, and no AI source or conversation data is read to reconstruct past use.

Hidden or minimized windows, screen locking and suspension pause measurement. A valid renderer report renews a lease of at most five seconds, bounding stale elapsed time after reporting stops. Counters save atomically every 30 seconds and on normal quit; an abrupt exit can lose unsaved totals. Time describes pet-window exposure, without inspecting other windows for occlusion or measuring user attention. The studio shows zero-use images, per-character time shares and an explicit confirmation before resetting both characters. These aggregates remain accessible to other programs running as the same Windows user and never authorize commands or change pose weights.

## Operating-system access

Detection is optional and can be disabled. Its fixed helper checks only `codex` and `claude` process names, the foreground handle and owning basename, and window/monitor rectangles needed to suppress the pet during fullscreen use. The main app receives only a closed provider/presence/geometry schema. Access denied and exited-process cases result in unknown. It runs hidden without user profiles, inherited interactive input, dynamic command strings, or arbitrary script paths, and stops when unused or on app exit. Manual character pinning does not stop presence detection while dormancy or fullscreen hiding still needs it. A process-scoped `-ExecutionPolicy Bypass` runs this project's reviewed helper; this does not modify registry execution policy. See [PowerShell's command-line documentation](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1).

The optional start-at-sign-in setting writes only `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Aipet`, using the app's fixed direct launch specification and `--background`. It reads only its own Run and StartupApproved values for status, never other startup commands, and never changes Windows approval or Application Control policies. No administrator privileges, service, scheduled task or watchdog are used. Quit ends the tray process until another explicit launch or the next login. See [startup boundaries](startup.md).

The main process runs with the user's ordinary privileges. This is not an operating-system sandbox: trusted application code can access more than the minimum data described here. Keep that code small and review new filesystem/network/process capabilities carefully. Do not request administrator rights, install services, capture the clipboard, register keyboard hooks, attach debuggers, or inspect browser profiles.

## Networking, updates, and dependencies

Runtime behavior has no intentional outbound service calls, telemetry, remote fonts, asset fetching, or automatic updater. Local activity uses files rather than sockets. Renderer requests are blocked independently of the network environment. Six snapshots of all measured application processes found zero TCP connections/listeners or UDP endpoints during isolated dormant, single-companion and dual-companion animated phases. This is not packet capture or OS firewall enforcement; short-lived traffic between samples is outside that evidence. [Performance record](performance.md).

Development dependency installation and asset retrieval require network access; these are separate from running the installed application. Use a lockfile and review dependency changes. Do not run upstream scripts as part of asset import. Electron bundles Chromium/Node, so manual framework security updates remain necessary even for a private app; no updater means those patches are the owner's responsibility.

## Review evidence and limitations

The accompanying implementation and tests should demonstrate the controls above. A successful unit suite does not establish behavior of the Windows compositor, prove the absence of all framework networking, audit npm's complete dependency tree, or certify a production build. Record exactly which controls were inspected and which runtime checks ran in the project README or test output. Do not label simulated activity as live integration.

Real Claude Desktop tool/completion metadata and native Windows local Codex tool metadata have been verified. The user completed Codex's review of all ten hooks in its desktop dialog; a fresh read-only check then confirmed all ten enabled and trusted. No trust bypass was used and no hook definition was changed to achieve delivery. Process detection supplies identity only. Reading transcripts to infer missing states would violate this design. Unverified or unsupported activity must remain idle or unknown.
