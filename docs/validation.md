## Resting-label investigation

During October 23 local validation, both pets were reported to display Resting while work continued. A metadata-only watch observed six fresh Codex tool/thinking updates in 20 seconds, with no Claude entries in Aipet's known inboxes. All ten Codex hooks remained enabled and trusted. A newer Codex conversation changed the pet correctly, while the unresponsive Codex and Claude sessions were already open before hook setup.

Isolated eight-hour clock-advance tests, inbox replacement checks, a forced test-renderer crash and a production-throttling hidden-renderer probe did not reproduce a persistent idle latch. An old session's hook-loading state is a plausible remaining explanation, not a documented or verified root cause. Current per-conversation delivery remains unverified until those sessions emit fresh metadata. No active AI task was interrupted, and no AI transcripts, databases, credentials, arguments or titles were inspected.

Two independent limitations were addressed: missing signals now have an honest badge, and Claude's documented hook session environment identifier separates simultaneous chats without reading stdin. Fixed Codex hooks still share an anonymous provider slot. Long operations can also outlive the 15-minute event lifetime without a fresh lifecycle event. The new diagnostics and polling recovery improve observability and resilience; they are not evidence that absent host events have been repaired.

After a Codex restart, the same behavior was reported in an existing local chat in a second project. A fresh metadata-only backend check discovered ten enabled, trusted Aipet hooks with no warnings in both that project and Aipet's project. This verifies current hook discovery by directory, not the configuration or delivery of an individual running lane. A tiny reply was sent in a second lane while the first lane remained busy; its outcome cannot establish delivery from the first lane. Temporary opt-in debug recording now distinguishes workspace signals using a hash and traces delivery into Aipet's main and renderer states. It does not distinguish individual lanes in one workspace, and the missed first-lane activity remains unresolved.

An October 24 capture scheduled for 25 minutes used two segments. It started on time, but its external timer missed the midpoint rotation and resumed three minutes after the requested window ended; the first segment expired after 15 minutes and no second segment was created. The saved metadata contains only initial completion/idle states and no hook arrivals. There may have been no test interaction during that window, so this is not evidence of failed delivery from the problematic chat. The replacement design arms one bounded start/end window in advance and shares clock gating between the bridge, app and recorder, eliminating midpoint renewal.

The replacement 20-minute window retained 59 valid records, all within the requested bounds and below the retention limit. Six hook invocations/writes from the Aipet workspace arrived during the first 18 seconds as its active chat finished; all six writes were accepted, and the Codex main/renderer state transitions agreed. No hook record from the second project or another workspace appeared. Ongoing work and four or five exchanges were reported in the problematic chat during this period. This points toward absent delivery before Node's bridge entry rather than a reproduced display-state failure. The trace cannot distinguish a skipped hook from a launcher that never starts Node, and it is not a complete execution audit.

An isolated launcher probe reproduced a separate concrete failure with the unchanged trusted command: CMD's standard argument escaping caused the nested PowerShell script to be printed rather than executed, with exit code zero and no event. A Windows-specific encoded override containing exactly the readable command's fixed script passed all ten handlers in each of four shell invocation forms (40 checks). The affected chat's actual launcher remains unverified, so this is supported portability hardening rather than a confirmed root cause for that chat.

## Performance and privacy limits

One updated isolated six-phase measurement recorded dormant, idle, single coding, dual reading/coding, reduced-motion single coding and returned-dormant behavior. Dormancy had zero application windows; two companions shared one window and the same four Electron processes as one visible companion. Dual activity measured roughly 360.5 MiB summed working set and 0.175% whole-machine CPU in this short sample, plus a separate roughly 114.7 MiB PowerShell helper. Six successful socket snapshots across measured application PIDs found zero TCP connections/listeners or UDP endpoints. This is not packet capture, continuous monitoring or firewall enforcement. [Measurements and methodology](performance.md).

Mixed-DPI/multiple monitors, physical monitor unplug and next-login scheduling were not exercised. No claim of perfect compositor behavior or zero packets follows from these tests. No AI account stores, conversation files, internal databases, screen text, process arguments or other projects’ source were read for integration validation.
